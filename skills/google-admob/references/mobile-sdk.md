# Integrate AdMob in a native mobile app

## Inspect the project

1. Identify the app module or target, package or bundle ID, development variant, UI framework, and requested ad format and placement.
2. Find the resolved Google Mobile Ads SDK and mediation adapters, the app and ad unit configuration, the consent flow, and the code that owns ad loading and presentation. Reuse those entry points and the project's dependency conventions.
3. Check the SDK and adapter prerequisites against the project's build tools and supported OS versions. Read the ad format guide from the matching platform and SDK quickstart. Use the framework's own integration guide for Flutter or Unity projects. [Flutter quickstart](https://developers.google.com/admob/flutter/quick-start) · [Unity quickstart](https://developers.google.com/admob/unity/quick-start)

The app ID (`ca-app-pub-…~…`) identifies the app for SDK setup. The ad unit ID (`ca-app-pub-…/…`) identifies a placement for ad requests. For production configuration, use IDs supplied by the project or verified in the intended AdMob app and confirm that each ad unit matches the platform and format. [Find an app ID or ad unit ID](https://support.google.com/admob/answer/7356431)

## Android

- Look for the resolved Gradle coordinate and imports. GMA Next-Gen uses `com.google.android.libraries.ads.mobile.sdk:ads-mobile-sdk` and `com.google.android.libraries.ads.mobile.sdk` APIs. Legacy uses `com.google.android.gms:play-services-ads` and `com.google.android.gms.ads` APIs. Keep the project's existing SDK family for a placement change. For a new integration, check the current Next-Gen prerequisites and adapter compatibility before selecting the SDK. [Next-Gen quickstart](https://developers.google.com/admob/android/next-gen/quick-start) · [Legacy quickstart](https://developers.google.com/admob/android/quick-start)
- For Next-Gen, pass the app ID to `InitializationConfig` and call `MobileAds.initialize()` on a background thread before using the ad APIs. For Legacy, place the app ID in `com.google.android.gms.ads.APPLICATION_ID` metadata under `<application>` in the merged manifest. The UMP SDK needs this manifest metadata for either family. For a requested migration, follow Google's dependency and adapter instructions, including the exclusions for Legacy modules pulled in by mediation adapters. [Next-Gen migration guide](https://developers.google.com/admob/android/next-gen/migration) · [Android UMP guide](https://developers.google.com/admob/android/privacy)

## iOS

- Check the target's existing Swift Package Manager, CocoaPods, or framework setup and install the SDK through that path. Use Google's Swift package for a fresh integration. Check the quickstart's CocoaPods availability and deployment target notes if the project uses pods. [iOS quickstart](https://developers.google.com/admob/ios/quick-start)
- Set `GADApplicationIdentifier` in the app target's effective `Info.plist`. Merge the documented `SKAdNetworkItems` entries with the project's existing entries. Initialize through the SDK's documented start method, such as `MobileAds.shared.start()` in current Swift examples. Present ads and consent forms from the active scene or view controller. [iOS quickstart](https://developers.google.com/admob/ios/quick-start) · [iOS UMP guide](https://developers.google.com/admob/ios/privacy)

## Consent, initialization, and loading

1. Confirm the app's Privacy & Messaging configuration for the message being tested. Request an updated UMP consent state on every launch and present any required form from the active activity or view controller. Expose a privacy options entry point when the SDK reports that it is required. Check the iOS privacy strategies guide when implementing App Tracking Transparency or an IDFA message. [Android UMP guide](https://developers.google.com/admob/android/privacy) · [iOS UMP guide](https://developers.google.com/admob/ios/privacy) · [iOS privacy strategies](https://developers.google.com/admob/ios/privacy/strategies)
2. Gate ad SDK startup and ad requests on UMP's `canRequestAds` result after starting the consent update. On a consent error, use that same result to determine whether a prior session allows requests. Apply relevant request flags at startup because SDK initialization can preload ads. With Android Next-Gen, pass first-request targeting settings through `InitializationConfig.Builder.setRequestConfiguration()`. Make startup idempotent across callbacks and wait for the initialization callback when using AdMob mediation. [Android UMP guide](https://developers.google.com/admob/android/privacy) · [Next-Gen targeting](https://developers.google.com/admob/android/next-gen/targeting) · [iOS UMP guide](https://developers.google.com/admob/ios/privacy) · [iOS mediation guide](https://developers.google.com/admob/ios/mediation)
3. Use the format-specific loading, presentation, and disposal APIs. Keep view ownership tied to the screen lifecycle, ignore callbacks for disposed screens, and avoid duplicate loads during recomposition or view updates. Clear a consumed full-screen ad reference and handle load failure, show failure, and dismissal so the underlying flow remains usable. For rewarded ads, grant the reward from the SDK reward callback.

For anchored adaptive banners, calculate the ad size from the measured container width and account for safe areas or window insets. With Android Legacy, call `AdView.loadAd()` on the main thread. Remove the banner from its container when the screen releases it and call the SDK's disposal API where applicable. [Next-Gen banners](https://developers.google.com/admob/android/next-gen/banner) · [Legacy banners](https://developers.google.com/admob/android/banner) · [iOS banners](https://developers.google.com/admob/ios/banner)

## Verify with test ads

1. Build the affected variant or target and run it on a device, emulator, or simulator. Use Google's demo ad unit for the correct platform and format. For an initial smoke test, use the matching sample app ID from the quickstart. To test consent messages configured for the app, use that app's ID with test ads. For the app's own ad units, verify test-device setup before interacting with ads. Enable test mode for each mediation network being exercised. [Next-Gen test ads](https://developers.google.com/admob/android/next-gen/test-ads) · [Legacy test ads](https://developers.google.com/admob/android/test-ads) · [iOS test ads](https://developers.google.com/admob/ios/test-ads)
2. Check cold launch, required consent and privacy options, load and show success, dismissal, navigation away during loading, and the no-fill or network failure path. Record the load error domain, code, and available response info, and use Ad Inspector on a test device to inspect requests and adapters. State which checks ran on a device and which were verified only by the build or code review. [Next-Gen load errors](https://developers.google.com/admob/android/next-gen/ad-load-errors) · [Legacy load errors](https://developers.google.com/admob/android/ad-load-errors) · [iOS load errors](https://developers.google.com/admob/ios/ad-load-errors) · [Next-Gen Ad Inspector](https://developers.google.com/admob/android/next-gen/ad-inspector) · [Legacy Ad Inspector](https://developers.google.com/admob/android/ad-inspector) · [iOS Ad Inspector](https://developers.google.com/admob/ios/ad-inspector)
3. Keep demo IDs and consent debug settings confined to development. For release preparation, inspect the release build configuration for the intended app and ad units and verify store linkage, app readiness, and `app-ads.txt` status where applicable. [App readiness](https://support.google.com/admob/answer/10564477) · [App verification](https://support.google.com/admob/answer/14538460)
